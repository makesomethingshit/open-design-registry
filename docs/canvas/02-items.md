## Invariants
- Stable item IDs and explicit `IMAGE` / `TEXT` kinds. A future replacement archives the old item and creates a new ID, preserving comments/provenance.
- Original design vs. external reference provenance is explicit; Canvas images do **not** inherit Project/Revision licenses.
- Server issues storage keys; never trust a client-provided `assetKey`. Image bytes must pass real PNG/JPEG signature, size and auth checks.
- Future upload and item writes must serialize with #130 approval/revocation and check fresh Project/public visibility.
- The asset proxy must enforce CanvasItem reference + current visibility; guessing a key is not authorization.
- `sortOrder` is a reading/list fallback only. #132 spatial location uses persisted coordinates, not this order.

## API, cleanup and author retention
- `GET/POST /api/projects/:slug/canvases/:canvasId/items`: read items, submit JSON TEXT metadata, or multipart IMAGE metadata with a `file` field. Only an approved Canvas owner writes; asset keys are always generated by the server. MIME, size and PNG/JPEG magic bytes are checked before upload.
- `DELETE .../items/:itemId` archives the item without changing its ID, bytes or provenance. Repeated archival is idempotent. Public approved history remains readable after revocation/reapplication; a private Project hides Canvas assets from everyone.
- Upload preflights permissions without holding a DB transaction open during S3 PUT. Attachment rechecks ACL under Project→Canvas locks. Permission loss, an ambiguous PUT rejection or DB failure attempts S3 deletion; simultaneous deletion failure propagates both errors.
- Run the existing `npm run storage:cleanup-documents -- --apply` job to retry unreferenced `canvas-items/` objects after the existing seven-day grace period. It retains active and archived DB references, commits a deletion marker before S3 DELETE, and serializes with final upload attachment using the existing advisory lock. Failed deletes remain discoverable on subsequent scans. Dry-run remains the default.
- Contributor account deletion anonymizes both Canvas owner and item author using `SET NULL`, preserving content/asset references. Full Project deletion still follows the existing Project lifecycle described in A.
- PostgreSQL with injected storage faults and actual S3-compatible protocol tests are separate suites. S3rver evidence is not MinIO or production S3 evidence; UI/browser and remote CI remain separate acceptance gates.
