# Contributor Canvas B — item and asset contract (#131)

Item creation, reading, archive, and replacement are exposed through `CanvasItemsPanel` in `src/components/canvas/canvas-items-panel.tsx`. `CanvasItemCard` in `src/components/canvas/canvas-item-card.tsx` is also exported for the spatial board to reuse. The standalone panel contract is `{ slug, canvasId, canEdit }`; the card contract is `{ item, selected?, readOnly?, busy?, onArchive?, onReplace? }`. The Canvas detail page mounts the composer; C reuses the cards on the spatial board.

## Invariants
- `IMAGE` and `TEXT` items have stable IDs. Replacement creates a new item and archives the old one only after the new item is saved; comments and provenance remain attached to the old ID.
- Original work and external references are visibly distinguished. Canvas items do **not** inherit Project or Revision licenses. A rights note records contributor-provided information and does not grant permission.
- The server issues storage keys and validates actual PNG/JPEG signatures and the 10 MiB image limit. Before parsing multipart data, it requires an approved Canvas owner and caps measured request-stream bytes at 10 MiB plus 64 KiB for metadata; Content-Length is only an early rejection hint. Unauthorized requests do not consume the body, and body reads hold no Project/Canvas locks. Client-provided `assetKey` values are rejected.
- Every write rechecks approval and project visibility while holding the Project→Canvas locks. A prior approval remains readable as public, read-only history after REVOKED or a reapplication to PENDING. `canEditCanvas` remains false in those states. A private Project hides Canvas metadata and assets from everyone.
- Asset reads check the item reference, moderation block, and current project/Canvas visibility before storage I/O and again after the response body is bounded and buffered. S3 download and stream reads run outside the Project/Canvas locks, have a 10-second deadline and abort/cancel on timeout or size/type rejection. The measured response body is capped at 10 MiB even when Content-Length is missing or inaccurate.
- `sortOrder` is a reading/list fallback only. #132 spatial location uses persisted coordinates, not this order.

## API, UI, cleanup and author retention
- `GET/POST /api/projects/:slug/canvases/:canvasId/items` reads items, accepts JSON TEXT metadata, or multipart IMAGE metadata with a `file` field. Public list responses expose the contributor name but omit the internal `authorId`, preserving stable item and asset identifiers and other stored fields. Only an approved Canvas owner writes. `DELETE .../items/:itemId` archives the item idempotently without changing its ID, bytes, or provenance.
- The owner composer accepts text or PNG/JPEG, alt text, source URL, and rights note. Cards show the contributor, original/reference label, source and rights note, image fallback/retry, and archived state. Replacements create a new ID, then archive the old item. If the archive request fails after creation, the UI reports the partial result and leaves both items available so the old item can be archived directly. If the create transport returns no response, the UI reports that the outcome is unknown, disables further submissions, and requires a reload to reconcile before another create; explicit HTTP errors remain retryable. Create requests are separate intents and are not replay-idempotent.
- `readCanvasAsset` performs a short locked authorization/reference check, fetches and buffers the object without DB locks, then repeats the locked check and moderation lookup. A private transition or new moderation block committed during storage I/O makes the response 404. A REVOKED Canvas with `firstApprovedAt`, including a PENDING reapplication, stays readable on a public Project under the A policy. Reads do not hold up a privacy change or revocation while S3 responds.
- Run the existing `npm run storage:cleanup-documents -- --apply` job to retry unreferenced `canvas-items/` objects after the existing seven-day grace period. It retains active and archived DB references, commits a deletion marker before S3 DELETE, and serializes with final upload attachment using the existing advisory lock. Failed deletes remain discoverable on subsequent scans. Dry-run remains the default.
- Contributor account deletion anonymizes Canvas owner and item author using `SET NULL`, preserving content and asset references. Full Project deletion follows the existing Project lifecycle described in A.
- Cleanup retains Canvas `sourceUrl` provenance references too. Matching is deliberately conservative: URL lookalikes may retain bytes. New own-storage source references serialize with cleanup and reject expired/deleted objects.
- PostgreSQL race tests use real transactions with delayed injected storage responses. S3 protocol tests use the configured S3rver endpoint and the dedicated `canvas-ready-b` bucket; this is not MinIO or AWS evidence. The item browser test passed at 390/320px with keyboard submission, actual image loading, source/rights labels, and recovery from archive transport failure after replacement. Membership and spatial-board browser tests are validated separately; final CI evidence is recorded in the PR body.
